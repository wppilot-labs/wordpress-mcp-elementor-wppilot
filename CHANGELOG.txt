v1.15.0 - 2026/09/28
* New: a redesigned admin. WPPilot opens on a Dashboard that answers "is everything fine, what did agents do, does anything need me": whether agents can act and under which safety profile, connected clients and when they were last active, changes in the last 24 hours and how many can be undone, writes waiting for approval, and the latest changes with an Undo button on each. The connection wizard, credentials and endpoints moved to their own Connect screen. Sixteen screens are grouped into six sections - Dashboard, Connect, Activity, Agent, Studio, Settings - with the screens of each section as tabs under the page title, and Activity shows a count when writes wait for approval. The look is calmer: hairline cards instead of heavy black borders, sentence-case labels, and green for "agents can act" instead of red. The header is one white bar with the site's name and the agents' state, and the toolbar shows "WPPilot" with a green, amber or grey dot instead of a red "WPPilot ON" block. Every screen now fits a phone without scrolling sideways.
* Prompts shows one industry at a time with the search still covering all of them, in a two-column grid; the screen was 94,000 pixels long with Pro's briefs. The free briefs' industries now match Pro's, so "Pets" and "Pets & animals" are no longer two categories.
* New: search and replace across posts. wppilot/search-replace-preview builds a reviewed plan - every match, per field, with before and after - over post titles, content, excerpts and chosen meta keys, serialized values and builder JSON included (Elementor's escaping is kept byte for byte). wppilot/search-replace-apply writes only posts that are in the plan and unchanged since the preview, 100 per call or as a background job, takes a before-image of exactly the fields it touches, and records one undoable change per post under one batch, so one post or the whole run can be undone. Serialized objects, guids and options are never touched; regular expressions are off unless asked for and bounded. wppilot/search-replace-status and wppilot/search-replace-cancel follow and stop a background run.
* New: image editing. wppilot/edit-image resizes, crops, rotates and flips an image as a new attachment or in place, the way WordPress's own image editor names files and keeps backup sizes, and either can be undone. The original file is never deleted.
* New: accessibility. wppilot/audit-accessibility reads a page as visitors receive it and checks it against WCAG 2.2 - language, title, headings, alt text, labels, accessible names, duplicate ids, ARIA references, landmarks, tab order, zoom lock, iframe titles and table headers - with the success criterion and level on every finding, a score, and what it could not check (contrast, focus, target size, script-rendered content). wppilot/audit-media-alt finds images with missing or filename alt text; wppilot/get-media-image shows an image to the model as MCP image content so it can write real alt text; wppilot/update-image-alt sets it in bulk with undo per image or per batch.
* New: content audit. wppilot/audit-content finds broken internal links, orphan pages, thin content, missing SEO descriptions and structured-data problems (and notes that FAQ and HowTo markup no longer earns Google rich results) across the site as a background job; wppilot/audit-content-status reports it.
* New: Block Notes. An agent can leave a note on a block for a person, reply, and resolve, and read the notes a person resolved - the review loop WordPress 7.1's Notes make possible. Every note it writes can be undone.
* New: site tools. WP-Cron list, run and delete (a deleted event can be put back at the same time and schedule), Site Health tests, transient flush, and - only on Developer Full Access, and recorded in the change log without their results - an options explorer and wppilot/database-query, one checked, read-only SELECT with sensitive columns redacted and the users, options and key tables refused.
* New: multisite. On a network, wppilot/network-list-sites and wppilot/network-run-ability run an ability on another site through that site's own safety profile, confirmation and gates, and record the change in that site's own log.
* New: Connection Doctor, on Diagnostics and as wppilot/connection-doctor. It finds what stops an MCP client connecting - a firewall, Cloudflare, ModSecurity, a stripped Authorization header, disabled Application Passwords, OAuth clock skew or URL mismatch - and gives the exact fix for the server it runs on.
* New: an MCP server card at /.well-known/mcp/server-card.json and an MCP Registry entry; skills and industry briefs served as skill:// resources; MCP Tasks, so a long call can run in the background and be polled or cancelled; and an MCP Apps preview card, which hosts that support it show beside a preview with an Apply button.
* New: a person, not the model, can confirm destructive calls. With Settings > Confirmation mode set to "A person approves", confirm=true from the model is no longer enough: the person approves the exact call in their MCP client, or on a one-time wp-admin link that shows exactly what will run. Each change records how it was confirmed. Off by default; existing connections behave as before.
* New: access tokens are agent identities. A token now has an expiry chosen at creation, can be limited to chosen abilities or categories, and can carry a safety-profile ceiling below the site's. Everything outside its scope is refused and hidden from it, and its changes are attributed to it by name.
* New: other plugins' abilities are governed like WPPilot's own. Any ability can be set to always require confirmation or a minimum profile on the Abilities screen, and a declarative ledger map lets writes by other plugins' abilities (Rank Math and SEOPress settings to start) be undone instead of recorded as irreversible.
* Changed: the change log is stored in its own database table instead of one option capped at 500 rows. Existing history is moved across on update, in order; if the table cannot be created the option keeps working and Diagnostics says why. The Changes screen and the export page through it in the database. History is kept for 10,000 changes or 90 days, and large before-images of changes older than 30 days are dropped.
* New: the features above are portable kits (includes/kits), each exportable into another plugin with scripts/export-kit.php.
* Elementor edits can be undone without Pro. The free Elementor writes (add, edit, move, duplicate, reorder and delete elements, set content and page settings) had no before-image, so on a site without Pro every one was recorded as "No supported before-image". Pro's own Elementor capture still takes over when Pro is active.

The check is now order-independent, and when an undo really does not match it names the fields that still differ.

The credential is now judged at REST authentication when nothing judged it earlier.

v1.14.0 - 2026/09/28
* Chat now runs every ability through the same controls as MCP and the REST API. It called the ability directly, so a Chat write skipped the write rate limit, the design gate and anything a companion plugin adds, such as Pro's approval queue. Every execution path - the modern MCP transport, WPPilot's REST route, WordPress core's ability runner, Chat and Pro's approval replay - now runs one gate pipeline: safety profile, confirmation, then the shared wppilot_pre_ability_execute filter. Chat's approve button is the confirmation, so the model is not asked for confirm=true there. The require-preview rule still stands aside for Chat, as its setting has always said. The modern-only wppilot_modern_mcp_pre_ability_execute filter is no longer fired; hook wppilot_pre_ability_execute, which now runs on that transport too.
* New screen: WPPilot > Changes. Code and skills have long said to undo a mistake "from the Changes screen", but there was no such screen; the only way back was the rollback-change ability, run by the same agent that made the mistake. The screen lists every recorded change newest first, filters by ability, agent, date range, status and kind, shows one change's redacted input, result and undo verification, and undoes one change, one bulk batch, or every undoable change a filter shows - all of one agent's work today, say - up to 200 at once, newest first, with a report of any that did not come back. The same filters download as CSV or JSON, without before-images; CSV cells that a spreadsheet would run as a formula are defused.
* New ability: wppilot/export-changes. The change record as flat rows for a client report or an audit, filtered like the Changes screen and paged 500 rows or 256 KB at a time. Before-images never leave the site.
* Undoing a change to a draft failed. A draft that was never scheduled has a floating date, and WordPress moves a floating date to "now" whenever the post is updated unless told the date is deliberate, so the undo put the content back and then failed its own check on the date, reporting "Rollback ran but the observed state did not match the before-image". It keeps the draft's date now.
* Bulk writes record one undoable change per item, grouped, so a batch can be undone as one or item by item, and one call cannot fill the change record: before-images stop after 1 MB per call and later items say plainly that none was kept. The change record is written under a database lock, so two writes recorded at the same moment can no longer erase each other.
* An ability can now keep a sensitive read off Production Safe and have every call recorded: meta.safety.min_profile names the least permissive profile it runs under, and meta.safety.audit_reads records who ran it and with what input, never what it returned. A read-only ability used to pass every profile, because its read-only flag was checked before anything else.
* Kits. A feature can now be built as a self-contained folder - kit.json, abilities, skill - on a small runtime that supplies the safety profile, confirmation, change record, undo and background jobs, so the same folder can be exported into another plugin with scripts/export-kit.php, renamed under that plugin's own prefix. wppilot/export-changes is the first. A kit that cannot load on this site says why instead of registering nothing.
* Modules can register how their own changes are undone (wppilot_register_rollback_strategy), so a write that keeps its own before-image is no longer recorded as impossible to undo.
* One new ability, read-only. No permission changes; existing connections keep working and do not need re-authorising.

v1.13.0 - 2026/09/26
* WPPilot no longer fatals beside another plugin that bundles the same dependencies. Composer derives the Jetpack autoloader's namespace from the dependency set, so two plugins with similar composer.json files generate the identical namespace and the second one to activate dies with "Cannot declare class Automattic\Jetpack\Autoloader\jp<hash>\al<version>\Autoloader, because the name is already in use" - a fatal that names a hashed class nobody can search for and reads as a WPPilot bug. The namespace is now pinned to one WPPilot owns, so it cannot collide with a hash another project happened to generate. On WP_DEBUG sites the autoloader's own conflict check is switched on as well, so the next collision of any kind is logged by name instead of appearing as a white screen.
* WPPilot now shares a site with Elementor's MCP, and with any other plugin that ships the WordPress MCP Adapter. Only one copy of the adapter can ever load - its classes are global and unprefixed - and which copy wins is decided by version arbitration across every plugin's classmap, so WPPilot can find itself running Elementor's copy. class_exists() cannot see this: it answers true whoever provided the class. WPPilot now resolves the adapter's actual origin and behaves accordingly. When the copy is its own, nothing changes. When it is not, WPPilot stops renaming the adapter's default server and stops claiming the legacy alias slug - that server belongs to the plugin that bundled the adapter - and registers /wp-json/mcp/wppilot explicitly instead, so every existing client configuration keeps working rather than 404ing the moment another MCP plugin is installed. Creating a server whose id is already taken is skipped rather than thrown, because that throw happens inside mcp_adapter_init and would take down every server on the site rather than one registration.
* wppilot/system-status reports which copy of the adapter is loaded, its version, and the plugin directory that owns it. On a site where MCP behaves oddly and more than one MCP plugin is installed, that is the first line to read.
* New ability: wppilot/elementor-audit-atomic-readiness. Elementor 4 introduced atomic elements, and the tooling built on them - Elementor's own MCP included - works on atomic documents. Every site built before that is classic widgets, and the failure is not an error message: the tool connects, reports success, and cannot edit the page anyone asked about. Nothing on the site says why. This reads every Elementor document rather than one, classifies every element, and answers it in one call: how much is already atomic, how much WPPilot can convert, which widget types block the rest and in how many documents. A widget whose plugin has been deactivated is reported as unregistered rather than counted as classic, because those elements are lost rather than converted and that has to be known before anybody starts.
* The classic-to-atomic equivalents the audit counts on live in one table the converter reads too, so an audit that calls a widget mappable and a converter that then cannot map it is not a state this can reach. A widget with no honest structural equivalent is absent from it: icon-list can be rebuilt as a flexbox of paragraphs, but that is a reconstruction with its own losses and belongs in a conversion report rather than in a table claiming equivalence.
* wppilot/verify-rendered-page can now check a page that is not published. It used to refuse - a draft has no public URL, and fetching one anonymously returns the 404 rather than the page - which sent the check away at exactly the moment it was most wanted, while the page was still a draft. The preview is now fetched carrying the caller's own session, opened for the request and destroyed as soon as it returns. Nothing is escalated: the cookies authenticate the current user and nobody else, they are valid for a minute, they are only ever attached to a URL on this site, and a caller who cannot read the draft in wp-admin cannot read it here. The result says it was a preview, and says what a preview does not exercise.
* New ability: wppilot/get-page-view-link. Every other check in WPPilot reads the page; none of them can see it. Whether a headline is legible over the photograph behind it, whether the third card wrapped onto its own row at 1024px - those are visual facts, and reading HTML answers none of them. Most AI clients already have a browser, so this closes the loop with the one they have rather than by building a renderer: it returns the URL to open and the three widths worth looking at. For a draft it says a signed-in browser is needed and names wppilot/create-admin-access-link, rather than minting a session itself: a read-only ability that handed out a wp-admin session would have walked past the critical rating, the confirmation and the safety profile that guard that link.
* Visual verification. Every other check in WPPilot reads the page; none of them could see it, and the failures that matter most to whoever owns the site are visual - a headline illegible over the photograph behind it, a card that wrapped onto its own row at 1024px, an element that rendered and is invisible. The rendered check has listed visual-regression and responsive-breakpoints under not_checked since it was written. This is that gap: wppilot/register-capture records a screenshot against the page it shows, wppilot/list-captures finds the one to compare against, and wppilot/compare-captures reports how much changed and exactly where.
* The comparison samples a grid of average colours rather than comparing pixels. A pixel-exact diff reports every page as changed - a font rasterises differently, an image is re-encoded, a carousel is on another slide - and a check that cries wolf is a check that gets switched off within a day. Adjacent changed cells are merged into regions, with one cell of slack so the gap between two words in a changed headline does not split one finding into two, and the regions come back in the coordinates of the newer image so they can be pointed at. A page that got taller is reported separately, because sampling normalises both images to the same grid and added content would otherwise shift every cell rather than show up as a region.
* WPPilot still bundles no renderer and never will: a headless browser inside a WordPress plugin is not something a shared host survives. The screenshot is taken by a browser that already exists - the AI client's own, through wppilot/get-page-view-link - and these abilities store what comes back and compare it. Captures are attachments and everything refers to one by id, because a preview record is capped at 256KB and the whole change ledger at 4MB: a base64 screenshot in either would evict real history to store a picture.
* Ten captures are kept per page, oldest pruned on write. Comparing two captures taken at different widths is answered with the comparison and a warning, because "everything changed" is true there and useless.
* A queued block-editor change whose target page was deleted stranded its whole batch. The queue already refused a missing target at commit, but an item never reached commit: it was handed to a browser tab that cannot open a post which is not there, and the tab had nothing useful to report back, so the item sat running until its lease expired and the batch never finished. The target is checked when the item is claimed now, so it fails once, names the reason, and the rest of the batch carries on.
* The Prompts screen is usable at three hundred briefs rather than ten. Every brief printed open, which came to 2.7MB of markup before anybody saw the first one; bodies are collapsed now - still in the page, so Copy and find-in-page reach them - and a filter sits above the sector headings.
* A brief's `scope` survives the parser. It says whether a brief builds a landing page, a whole site, a store, a course or a booking site; free's own briefs are all landing pages and leave it empty, and a field the normaliser dropped was one nothing could show or filter on.
* Five new abilities, one of them a write that only records an attachment as a capture. One existing ability widened. No permission changes; existing connections keep working and do not need re-authorising.

* The refusal for hand-written builder storage meta now routes through the same remedy helper the post_content refusal uses, so on a site without Pro it stops pointing at an ability that is not registered there.
* Fixed WordPress-core abilities being served by WPPilot Pro's older copies. Free registers on wp_abilities_api_init at priority 20 and skips any name already registered, on the assumption that it runs ahead of Pro's loaders. Registration order in fact follows plugin load order, and load order follows the active_plugins option, which records activation order rather than alphabetical order. On a site where Pro was activated before free, Pro's plugin file loaded first, its 23 core copies registered first, and free's duplicate guard then stood down — so every fix free had shipped to those abilities since 1.1.0, including the capability and privacy work in that release, was inert. Observed with free 1.4.0 and Pro 1.1.1 both active on WordPress 7.0.3, where wppilot/update-post resolved to Pro's callback. Pro 1.1.2 now stands aside whenever free is 1.1.0 or newer; the guard in free is unchanged, so a site still running an older Pro keeps that Pro's copies rather than losing the surface.

v1.4.0 - 2026/08/16
* Added access tokens, a third way to connect next to OAuth and application passwords. A long-lived `Authorization: Bearer wpp_...` credential for callers that have no browser and no interactive session: the Claude Messages API MCP connector, the OpenAI Responses API `mcp` tool, cron jobs, automation platforms, curl. Neither existing method reaches those — OAuth needs a browser sign-in and expires in an hour, and several of those callers cannot send HTTP Basic at all.
* Tokens are 256 bits from the CSPRNG, prefixed `wpp_`, and stored only as a SHA-256 digest, so a database dump yields no working credential. The plaintext is shown once at creation. Optional expiry of 30 days, 90 days, a year, or never; each token is revocable on its own, and every token belonging to a user is deleted with the user.
* A token borrows the capabilities of the account that created it, re-checked on every request rather than frozen at creation, so demoting or deleting that user closes the token in the same moment.
* The Bearer path decides which validator runs from the token prefix, never by trying one and falling back. A failed OAuth validation records an authentication error that denies the request outright, so a fallback would have meant every access token being rejected before it was looked at.
* Access tokens authenticate on the canonical `/wp-json/mcp/wppilot` endpoint — the URL every other snippet on the Connect screen already uses. The hosted API callers this credential exists for take one URL and one token with no way to say "use the other endpoint for this credential", so a second URL would have been one more thing to get wrong for no security gain: the endpoints mirror the same server. The OAuth route boundary is unchanged, and an unauthenticated request to the canonical endpoint still gets no OAuth challenge.
* Connections made with a token are recorded as their own method in the ledger and named by the token's label, rather than being filed under Application password because of the route they arrived on. The Overview screen lists the third transport alongside the other two.
* The Connect screen is now a three-card chooser. The access-token card is never the recommended one: it is the most powerful credential of the three, and it is offered as the answer to a specific problem rather than as an easy default.
* Per-client configuration for the new method covers seventeen clients plus the Claude API, the OpenAI API and curl, each written in the shape that client actually parses. Verified against current client documentation rather than assumed from each other: VS Code nests servers under `servers` where everyone else uses `mcpServers`; Antigravity and Devin Desktop expect `serverUrl` and ignore `url`; Cline spells the transport `streamableHttp` where Roo and Kilo spell it `streamable-http`; Codex uses TOML with `http_headers`; Zed has no HTTP transport at all and still needs the mcp-remote bridge.
* Client notes updated for August 2026. Claude Code shows a static-token server as "needs authentication" in /mcp because this site also advertises OAuth metadata — a display bug that does not stop the tools working, and the snippet now says so rather than leaving it to be diagnosed. The Droid command passes --no-oauth for the same reason. Roo Code was discontinued in May 2026; its entry stays so existing connections keep their name, with the note pointing new setups at Cline.
* Clients whose MCP servers are added through a hosted UI with no header field — Claude on the web, ChatGPT, Manus, the Codex desktop app — are deliberately absent from the token method. They can only authenticate through OAuth, and offering a snippet with nowhere to paste it would be the page inventing a route that does not exist.
* Creating a token now scrolls to — and focuses — the reveal, instead of posting the page back to the top with the one-time value several screens below the fold. The value is shown once and cannot be recovered, so landing above it was how someone lost the only copy. The reveal is followed by the three steps that actually connect a client and a button that jumps to the generated configuration, which opens on the first client rather than waiting for a tab click.
* The Overview gained an Access tokens block, between the connection stats and the endpoint table: what the credential is for, how many are live, when one was last used, and a link that opens the Connect screen with the method already selected. A method that only appeared three screens into the setup flow was a method nobody found. The endpoint row is relabelled "MCP endpoint (application password or access token)", because both header credentials authenticate there and naming only one sent people looking for an address that does not exist.
* Every connection method now also offers the configuration as a prompt for an AI coding agent — "let your AI coder set this up" — carrying the server name, the URL, the exact snippet, the file it belongs in, and rules that stop the agent inventing a transport or a field that was never mentioned. It is additive: the snippets, paths, connector buttons and step lists are all unchanged, and the prompt sits behind a toggle under them. The prompt for the password and token methods carries the credential, so it says so.

* Seven clients added: Kimi Code CLI, Qwen Code, Gemini CLI and ZCode (GLM) among the editors, and Mistral Le Chat, Perplexity and ChatGPT as first-class registry entries alongside Claude on the web and Manus. Each appears under every method it can actually use — the registry now knows 29 clients, with 24 access-token snippets, 23 OAuth entries and 20 application-password entries.
* Qwen Code and Gemini CLI name a remote server's URL `httpUrl`, not `url`, and get their own builder so that difference cannot be folded back into the shared one. A snippet carrying `url` parses there and then connects to nothing — no error, no tools — which is the hardest kind of wrong to diagnose from the client side.
* Web apps became their own entry on the chooser rather than a credential to guess at first. Someone whose AI is a browser tab does not know whether they want OAuth or a token, and had to pick one before they could find out their app was even supported; now they pick the app and are told which credentials it accepts, including the three that can take a bearer header instead of a sign-in.

* Rewrote the walkthroughs for the hosted web UIs against their August 2026 interfaces, and added the ones that were missing. ChatGPT's steps pointed at Settings, Security and login — developer mode moved to Settings, Apps, Advanced settings, and the connector is created with Create app on the Apps screen; workspace plans need an admin to allow it first under Permissions & roles. Claude on the web moved from Settings to Customize, and on Team or Enterprise an Owner must add the connector under Organization settings before members can connect. Both now also say to switch the connector on in the chat, which is off by default and is the usual reason a correctly-added server appears to do nothing.
* Added Mistral Le Chat, Perplexity and a real Manus walkthrough, each with its own menu path: Connectors, Add Connector, Custom MCP Connector for Le Chat; Settings, Connectors for Perplexity (Pro, Max or Enterprise); Settings, Connectors, Add connectors, Custom MCP, Direct configuration for Manus.
* Three of the web UIs now accept an access token, not only OAuth: claude.ai stores request headers per connector (in beta, and the Authorization value must include the word Bearer), Le Chat offers an HTTP Bearer Token option, and Perplexity takes a bearer token. Each has click-through steps under the access-token method. ChatGPT, Manus and the Codex desktop app have no header field, so they stay OAuth-only and are deliberately absent from that method rather than shown with instructions that cannot be followed.
* Fixed the method chooser, which rendered as three mismatched boxes stacked down the page. The wrapper element the cards are laid out in had been dropped when the cards were split into their own function, so every card sized itself to its own text with no grid around it. The layout is now a grid with equal tracks rather than wrapped flex, which also stops a wrapped third card sitting alone at a third of the width.
* The Connect a client steps moved above the Overview panels. The screen was ordered state-then-action — five stat panels, the client list, the licence and the ability inventory, and only then the steps that connect something — so arriving with nothing connected meant scrolling past every panel to reach the only thing that could change that. Enable AI Abilities stays last: it is the off switch for a connection that already exists, not a step in making one.
* A method is now selected when the page opens, and each method's configuration section opens on its first client. Before, step 2 was hidden until something was clicked, so the page read 1, 3, 4 — a numbered sequence with a hole in it — and the OAuth panel showed a row of client tabs above an empty space, which reads as "this method has no instructions". The AI-coder prompt was inside that empty space, which is why it could not be found.
* The initial selection runs on DOMContentLoaded rather than inline. The chooser's script is emitted before the section it reveals, so running it immediately called getElementById on an element the parser had not reached yet and silently did nothing.

* The AI-coder prompt was rewritten to be worth pasting. It now numbers its rules, tells the agent to update an existing entry for this server rather than adding a second, forbids trying other URLs and transports "to see what sticks", and — for the two methods that carry a credential — forbids committing or echoing it. It ends with a verification section that says what a working connection looks like (a long tool list whose names begin with wppilot_, then one read-only discover-abilities call that reports the site's safety profile), and a per-method list of behaviour that looks like a fault and is not: the "needs authentication" label a static token provokes, the npx cold start, the stripped Authorization header behind a 401, and OAuth's normal re-authorization prompts. Those last ones exist because an agent that treats them as bugs will "fix" a working connection into a broken one.
* Every hint under a generated snippet now says what success looks like rather than only where the file is. The two failures the Connect screen actually produces are not restarting the client and treating a saved configuration as a working connection, so the OAuth hint says a sign-in prompt is the expected next thing and that the snippet holds no secret, and the access-token hint says no sign-in follows and the tools should simply appear.
* The access-token configuration section renders a step list for a client that has no configuration file, so a hosted UI no longer has to be described as though it had one — and the AI-coder prompt carries those steps instead of a snippet.

* Fifteen unit tests cover credential-shape detection, digesting, and the route boundary, including a regression guard proving the canonical endpoint still advertises no required scope to an unauthenticated request — the property that keeps every existing application-password install working.

v1.3.0 - 2026/08/15
* Fixed restore-revision, which could not run at all on 1.1.0 through 1.2.1. The change ledger captures a before-image on every ability call, and its capture for this ability handed wp_get_post_revision() a cast expression. That parameter is declared by reference, so PHP 8 raised "Argument #1 ($post) could not be passed by reference" — a fatal Error, not a notice, with nothing in the MCP layer catching it. Every call returned a 500 before touching the post.
* Behind that fatal, the ability read failure as success. wp_restore_post_revision() answers null on error, false when the revision carried no restorable fields, and the post id on success; only null was refused. A false answer returned a success payload naming a post that had never been written, and the is_wp_error() branch guarding it was unreachable because that function does not return one. Only a positive id is accepted now, which also covers the 0 that wp_update_post() answers when it refuses a write.
* Change ledger entries now name the agent behind the write, not only the WordPress user. Claude Code, Cursor and Codex connect as the same administrator on most sites, so the user alone could not say which of them made a change. The credential can: an OAuth client id or an application-password UUID is issued per agent and is stable across its requests. Entries carry the credential, its label, and the client name and version the agent introduced itself with, and list-changes returns them.
* Identity is resolved once, at the MCP entry point, because that is the only place both halves are reachable — the credential comes from request-local OAuth state or WordPress' application-password global, and the client name needs the request object. The ledger reads it back later in the same request.
* A write with no agent behind it — wp-admin, WP-CLI, cron, another plugin calling an ability directly — is recorded as direct rather than credited to the last agent seen. OAuth client ids are stored hashed, as they already were in the connections table.
* Six unit tests cover both failures, against doubles that reproduce the WordPress contracts exactly: wp_get_post_revision() declares its parameter by reference, so calling it is the assertion, and wp_restore_post_revision() can answer all three of its documented shapes. Reverting either fix fails the suite.
* Added mago.toml. The analyzer shipped in require-dev since 1.0.0 with no configuration, so it answered "No files found to lint" and never ran — it is what found the by-reference fatal. php-version is pinned to the plugin's declared 8.0 floor, so 8.1-only syntax is reported rather than shipped to sites the plugin claims to support.

v1.2.1 - 2026/08/14
* Fixed search-extensions against the themes directory. themes_api() returns author as a WordPress.org profile record where plugins_api() returns an HTML link, so the string cast raised "Array to string conversion" on every theme search and handed the agent the literal word "Array" as the author.

v1.2.0 - 2026/08/14
* Added the plugin and theme lifecycle to WPPilot Free. Agents can search the WordPress.org directory, read one plugin or theme in detail, activate, deactivate, update, switch themes, install, and delete. Previously the only extension ability was list-extensions, so an agent could see what was installed and change none of it.
* Eleven new abilities: search-extensions, get-extension, activate-plugin, deactivate-plugin, update-plugin, update-theme, switch-theme, install-plugin, install-theme, delete-plugin, delete-theme. Free ability count is now 103, up from 92.
* Safety classification follows what each operation does to the server. Install and delete fetch and write executable code, so they are critical: blocked by Production Safe and Read Only, and available in Developer Full Access with explicit confirmation. Activation, deactivation, updates, and theme switches fetch nothing and write no files, so they remain available on a live site — but each one can take a site down, so all four are confirmation-gated.
* The lifecycle fragments added to the destructive classifier are specific names rather than bare update-/activate- prefixes, so update-post, update-media, update-term, update-menu, update-site-settings, and activate-design are not dragged into the confirmation path.
* DISALLOW_FILE_MODS is honoured through wp_is_file_mod_allowed() before any file operation begins, so a site that has opted out of code changes gets a named refusal instead of a partial install.
* Direct filesystem access is required and checked up front. WPPilot runs headless, where request_filesystem_credentials() has no screen to render an FTP form on, so any other method is refused with the method WordPress selected rather than stalling or half-writing.
* Security: WPPilot and WPPilot Pro cannot be deactivated or deleted through these abilities. Doing so mid-call severs the connection carrying the call and, on a remote site, removes the way back in.
* Security: delete-plugin refuses an active plugin. WordPress's own delete_plugins() does not check — the Plugins screen refuses before calling — and deleting files under a running plugin fatals the site on the next request. delete-theme refuses the active theme and the parent of an active child theme for the same reason.
* Security: slugs and plugin files are path-validated through validate_file() and a plain-directory-name pattern before use, because WordPress concatenates a stylesheet straight into a filesystem path. Package URLs for ZIP installs must be HTTPS.
* Installs leave the plugin inactive and the theme unswitched. Activation is a separate, separately confirmed call, so the review step cannot be skipped by an agent that only meant to install.
* Change ledger covers the new mutations. Activation, deactivation, and theme switches record a before-image and roll back with verification; installs, updates, and deletions are recorded as non-reversible, each stating the real reason and the manual path back.
* Update abilities refresh the update transient before deciding, so a site whose last check predates a release no longer reports "up to date" incorrectly, and report the version before and after.

v1.1.0 - 2026/08/13
* WordPress core abilities now ship in WPPilot Free. Content, taxonomies, media, comments, revisions, menus, user reads, and the allowlisted settings surface work with Free alone, with no Pro plugin, licence, or entitlement service involved. Pro remains the home of plugin-aware integrations: page builders, WooCommerce, forms, SEO suites, custom fields, themes, and multilingual.
* Added terms and taxonomies: discovery, listing, reading, creation, updates, confirmed deletion, and assignment to content, each enforcing the taxonomy's own manage_terms/edit_terms/delete_terms/assign_terms capability rather than assuming manage_categories.
* Added comments: listing and reading with commenter email and IP withheld from accounts that cannot moderate, plus creation, editing, approve/hold/spam/unspam/trash/restore moderation, and confirmed permanent deletion.
* Added revisions: listing with autosaves distinguished from saved revisions, reading with a direct comparison against the live post, and restoration recorded as a reversible write.
* Added menu containers and placement: create, rename, confirmed deletion, theme-location listing and assignment, and whole-menu reordering validated before any item moves.
* Added featured-image set/remove and media attach/detach.
* Added post restoration from the trash, reporting the status WordPress actually restored to.
* Free ability count is now 92, up from 42.
* Security: create-post, update-post, and delete-post previously ran on a single manage_options check and never consulted the post type's own capability object. They now enforce create_posts, publish_posts, edit_others_posts, edit_post, and delete_post read from the registered type, so a custom post type declaring its own capability set is no longer satisfied by edit_posts, and object ownership is honoured.
* Security: menu item URLs are validated against WordPress's allowed protocols before storage. A javascript:, data:, or vbscript: URL was previously stored verbatim and rendered into an href.
* Draft-first content creation is enforced in code rather than by schema default alone. Absent, blank, mistyped, and unrecognised statuses all resolve to draft before the capability gate reads them, so content cannot be published by omission or by a malformed value through any entry point.
* Generic content wrappers now refuse internal and plugin-private post types and taxonomies, so agents cannot write rows the owning subsystem never validates.
* Change ledger covers the new mutations, with before-images and verified rollback for term edits, comment edits and moderation, menu location assignment, and menu ordering. Permanent term, menu, and comment deletions are recorded as non-reversible with the reason stated.
* Added the repository's first automated test suite: unit tests running against WordPress function doubles, with no database required.
* MCP 2026-07-28 is now served alongside 2025-11-25. The modern revision is stateless — no initialize handshake and no session — and a request is served under it only when it carries modern per-request _meta. Legacy clients are unaffected and do not need to reconnect.
* Modern requests validate the mirrored MCP-Protocol-Version, Mcp-Method, and Mcp-Name headers against the request body, which is authoritative. Header names compare case-insensitively, Base64 sentinel values are decoded before comparison, and mismatches return HeaderMismatch (-32020). Unsupported versions return UnsupportedProtocolVersion (-32022) listing what this build serves.
* Implemented server/discover. It advertises both supported versions and only the capabilities actually registered on the site.
* Subscriptions, the tasks extension, and logging are deliberately not advertised: WPPilot has no change-notification producer, so subscriptions/listen would hold a stream open and deliver nothing.
* Modern list and read results carry bounded ttlMs and cacheScope "private" — never "public", because the ability list is filtered by the connected account's capabilities, by the active safety profile, and by per-site ability switches. Tools are returned in a deterministic order.
* Methods the modern revision removed (ping, logging/setLevel, initialize, resources/subscribe, resources/unsubscribe, notifications/roots/list_changed) answer method-not-found under 2026-07-28 and continue to work under the legacy adapter.
* Added Client ID Metadata Document support as the preferred modern OAuth registration path, advertised as client_id_metadata_document_supported. Dynamic Client Registration remains available as a fallback. Documents are fetched only over HTTPS from hosts that resolve exclusively to public addresses; loopback, private, carrier-grade NAT, link-local (including the cloud instance-metadata address), documentation, benchmarking, multicast, and reserved ranges are refused, IPv4-mapped IPv6 addresses are unwrapped before checking, every resolved address is checked to blunt DNS rebinding, and each redirect target is revalidated. Response size, timeout, redirect count, and JSON depth are bounded, logo URLs are never dereferenced, and fetch failures never report the address that failed.
* Redirect URIs are compared exactly and validated against the declared application_type, and authorization_response_iss_parameter_supported is advertised per RFC 9207.
